# Cython Decoder CPU Reduction - TDD Sub-Increment Breakdown

**Parent Increment:** C1 - Compile the JT128 spherical decode hot path for ARM64 production
**Goal:** Reduce the Intersection Monitor `lidar-decode` thread CPU load without changing the
`lidar2numpy.Decoder` public behavior or decoded frame contract.
**Date:** 2026-07-14
**Readiness:** Ready with approved assumptions and two non-blocking external inputs
**Primary repository:** `/Users/sean-SSP/Documents/code/lidar2numpy`
**Integration repository:** `/Users/sean-SSP/Documents/code/intersection_monitor`

## Target Outcome

The increment is complete when an ARM64 Intersection Monitor Debian package:

- contains a native CPython 3.12 `lidar2numpy` extension for the spherical decode hot path;
- refuses to build, install as a production artifact, or start `im-perception` in production mode
  when the compiled backend is unavailable;
- retains an explicitly selectable Python backend for development, tests, benchmarking, and
  rollback comparison;
- produces frames and errors equivalent to the current Python implementation for supported
  single- and dual-return JT128 packets;
- reduces `lidar-decode` thread CPU by at least 25% relative in both return modes on the target
  ARM64 device, with a target reduction of 35%; and
- does not introduce packet-queue backlog, frame incompleteness, kernel UDP drops, or material
  decoder latency regressions.

The user-reported starting point is approximately 45-50% of one core in single-return mode and
75% in dual-return mode. These numbers motivate the increment but are not the controlled baseline;
Sub-Increment C1.1 records the repeatable baseline used for acceptance.

### Codebase findings

1. `main` already contains an optimized dense spherical path that writes directly into the
   frame assembler buffer. The compiled candidate must be compared against this implementation,
   not the older allocate-and-concatenate path.
2. The Python fast path still creates two NumPy packet views, two masks, counts nonzero returns,
   dispatches several structured-field assignments per block, and parses the tail through Python
   objects. This is the bounded Cython target.
3. The current packed dtypes are not naturally aligned: `SPHERICAL_DTYPE` is 24 bytes with its
   `float64` timestamp at offset 14, and `POINT_DTYPE` is 28 bytes with its timestamp at offset 18.
   Native code must use the verified NumPy offsets or safe byte copies; it must not cast the output
   to a normally aligned C struct.
4. Intersection Monitor already isolates socket drain from decode. Decoder CPU/backlog can be
   evaluated using the `lidar-decode` thread together with `packet_queue_overwrites`, frame
   completeness, and kernel UDP counters.
5. The current Debian script's `ARCH=arm64` value labels the package; it does not cross-compile a
   native Python extension. The production build must prove it is running on native ARM64 Linux.
6. `AGENTS.md` and `CLAUDE.md` currently say no C/C++ and describe dual return as unimplemented.
   Those statements are stale: dual-return mode has already been implemented and used, and the
   user has explicitly authorized breaking the native-code prohibition for this bounded Cython
   decoder optimization. Those durable instructions must be corrected before implementation work
   is handed to agents.
7. `uv add` does not manage PEP 517 `[build-system].requires`. Runtime/development dependencies
   must still be changed with `uv add` / `uv add --dev`; the required build-backend declaration is
   a controlled packaging edit and should be documented as such in the updated agent instructions.

## Approved Assumptions

- **ASSUMPTION-1 - Performance objective:** Optimize `lidar-decode` thread CPU specifically.
  Whole-process or downstream pipeline reductions are useful secondary observations, not the
  acceptance metric.
- **ASSUMPTION-2 - Target architecture:** ARM64 Linux is the only production target for this
  increment. x86_64 will be added through a later target-architecture increment if needed.
- **ASSUMPTION-3 - Filter sequencing:** Build and evaluate the compiled backend against the
  current unfiltered production decoder first. Evaluate the filter independently later.
- **ASSUMPTION-4 - Backend policy:** Development and tests may use the Python fallback. Production
  Debian builds and packaged `im-perception` startup require the compiled backend and must not
  silently fall back.
- **ASSUMPTION-5 - Distribution:** This is an internal Debian-only distribution. Do not build a
  general PyPI wheel matrix or stable-ABI strategy.
- **ASSUMPTION-6 - Performance gate:** A 25% relative reduction in `lidar-decode` thread CPU in
  both return modes is the minimum worthwhile result; 35% is the target. Record both relative
  reduction and absolute percentage-point reduction.
- **ASSUMPTION-7 - Implementation boundary and explicit rule exception:** The prior blanket
  prohibition on C/C++ is superseded for this increment. Use a narrow Cython-generated extension
  behind the existing Python public API. Do not expand that exception into handwritten C/C++,
  unrelated native modules, or vendor SDK integration.
- **ASSUMPTION-8 - Failure policy:** Absence of the extension may activate the Python fallback in
  development. An extension that exists but fails to load because of ABI/symbol corruption must
  surface the import failure rather than being mistaken for an ordinary absent-extension case.

## Global TDD and Commit Rules

Every code-bearing sub-increment follows this sequence:

1. Add or change the smallest focused tests first.
2. Run the focused test and confirm the expected failure for the intended reason.
3. Commit the failing contract tests before implementation, as required by `AGENTS.md`.
4. Implement only that sub-increment.
5. Run focused tests, then the full library checks.
6. Commit implementation only after the checks pass.

Do not combine tests and implementation into one commit. Do not modify `uv.lock` by hand. Use
`uv add` or `uv add --dev` for managed project/development dependencies.

## Risks Surfaced During Decomposition

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Packed, unaligned NumPy output fields | Native crash or corrupt timestamps, especially on ARM64. | Assert dtype layout, use safe offset-based writes/copies, retain differential tests, scope unsafe directives narrowly. |
| Cythonized existing Python without typed-loop redesign | Build complexity with little CPU benefit. | Keep the minimal extension as a build milestone only; performance candidate must remove measured Python/NumPy operations. |
| Broken extension silently falls back | Production unexpectedly returns to 45-75% decoder CPU. | Distinguish absent module from broken import; package and runtime explicitly require compiled backend. |
| Mislabeled cross-architecture Debian build | Package installs but extension cannot import. | Native ARM64 guard plus wheel tag, clean import, and smoke decode before `fpm`. |
| NumPy C-ABI mismatch | Import failure after package dependency resolution. | Build against NumPy 2.x, record exact versions, import from staged and installed environments, test the final artifact. |
| GIL release or disabled checks applied too broadly | Races, segfaults, or memory corruption. | Validate buffers with GIL, release only typed loops, add checks incrementally after correctness. |
| Python and Cython paths drift | Tests pass on one backend while production differs. | Python remains oracle; differential suite runs both backends on deterministic and randomized packets. |
| Benchmark measures replay or timing overhead instead of decoder CPU | False performance conclusion. | Use raw packets, aggregate CPU/wall throughput, then live `lidar-decode` thread CPU for acceptance. |
| Filter branch changes the same hot loop | Duplicate work or incompatible native interface. | Finish unfiltered evidence first; integrate only the validated, merged filter contract in a follow-on. |
| Build-backend change omits package data | Default calibration fails only after wheel install. | Inspect/install wheel and run default-calibration tests outside source checkout. |
| Package provenance schema grows without support-model updates | Build facts exist but are invisible or rejected. | Add tests for build-info generation and support projection together in C1.8. |

## Rollback Strategy

- Keep the Python backend intact and continuously tested.
- Before production enforcement, rollback is backend selection to Python.
- After production enforcement, rollback is installing the last known Python-only Debian package or
  rebuilding a validation package with the production-require flag removed; do not silently mutate
  an installed production service.
- If the extension fails correctness, safety, or the 25% CPU gate, stop after C1.9 and retain the
  current optimized Python implementation.
- Do not delete the benchmark/equivalence harness if the candidate is rejected; it remains useful
  for future Python, Cython, or filter optimization work.
